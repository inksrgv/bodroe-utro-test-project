# Бодрое утро — единый сервис лояльности (прототип)

Прототип к ПР «От требований к прототипу (vibe coding)».
Кейс 4: сеть кофеен «Бодрое утро», 60 точек, единая программа лояльности.

## Что реализовано

Требование с наивысшим приоритетом из ПР3/ПР4 — **единый бонусный баланс, доступный
и в мобильном приложении, и на оффлайн-кассе** (инкремент 1, MVP).

## Архитектура (и почему такая)

```
касса POS-01…05 ─┐
                 ├─→ HTTP API (FastAPI) ─→ журнал операций (SQLite / ledger)
приложение ──────┘                          ↑
                                     баланс = SUM(points)
```

Три решения, каждое закрывает конкретное требование:

1. **Баланс не хранится, а вычисляется как сумма проводок.** Отдельного поля `balance`
   нет — иначе при сбое синхронизации два канала разойдутся, а это и есть исходная
   проблема кейса. Журнал — единственный источник истины (FR-04, NFR-02).
2. **Идемпотентность через `UNIQUE(idempotency_key)`.** Ключ генерирует касса/приложение
   на один чек. Повторная отправка того же ключа возвращает прежний результат, а не
   проводит операцию снова (FR-15, защита от двойного списания при обрыве связи).
3. **`BEGIN IMMEDIATE` на транзакцию.** Два параллельных списания не могут одновременно
   прочитать один остаток и уйти в минус (FR-08). Тест `test_concurrent_redemption_cannot_overdraw`
   запускает 10 списаний по 50 б. при балансе 100 б. и требует ровно 2 успеха и остаток 0.

## Что НЕ реализовано (сознательно, вне MVP)

FR-01, FR-11…FR-14, FR-18…FR-22, FR-24, FR-25 — по распределению из ПР3 это инкременты 2–3:
регистрация профиля, конструктор правил и статусов, миграция баллов, аналитика.
В прототипе для них есть только точки расширения (таблица `customers.status`,
константы правил в `app/loyalty.py`).
