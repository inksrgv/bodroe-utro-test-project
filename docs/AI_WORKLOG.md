# Журнал работы с AI-инструментом (по содержанию ПР)

Требование, выбранное для реализации: **единый бонусный баланс и статус клиента
во всех каналах** (БТ-01 из ПР1, US-01/US-02 из ПР2, FR-02…FR-10 + FR-15 из ПР3,
инкремент 1 MVP). Обоснование выбора: это требование с приоритетом «Высокий» в ПР3,
и оно же снимает исходную проблему кейса — «баллы в приложении нельзя потратить
на кассе и наоборот».

## 1. Постановка задачи на естественном языке

> Нужен сервис лояльности для сети кофеен. У клиента один бонусный баланс,
> который одинаково доступен и в мобильном приложении, и на оффлайн-кассе.
> Бариста должен найти клиента по карте или телефону, увидеть баланс и провести
> начисление или списание. Баланс не может уйти в минус. Одна и та же покупка
> не должна начислить или списать бонусы дважды, даже если касса отправит запрос
> повторно из-за обрыва связи. Операция на кассе — не дольше 5 секунд.

## 2. Ограничения, которые были заданы инструменту

- Не два баланса, а один источник истины (иначе проблема кейса не решается).
- Приложение и касса — равноправные клиенты одного HTTP API.
- Python + FastAPI + SQLite: без внешних сервисов, чтобы прототип запускался одной командой.
- Веб-интерфейс должен показывать кассу и приложение одновременно — чтобы расхождение
  баланса было видно наглядно, а не «на словах».
- Всё, что вне инкремента 1, не реализуется, но оставляется точкой расширения.

## 3. Предложенная структура решения

```
app/db.py       — схема, транзакции, вычисление баланса
app/loyalty.py  — правила: начисление, списание, отмена, идемпотентность
app/main.py     — HTTP API (FR-23)
app/static/     — экран кассы + экран приложения + журнал
app/seed.py     — демо-данные
tests/          — 14 проверок с привязкой к ID требований
```

Структура принята: она разделяет «правила» и «транспорт», поэтому при замене SQLite
на PostgreSQL или при добавлении конструктора правил (инкремент 3) меняется один слой.

## 4. Дефекты, найденные при тестировании, и исправления

| # | Что сломалось | Причина | Исправление |
|---|---|---|---|
| 1 | При списании начислялось слишком мало баллов, демо-сценарий не проходил | правило 5% от чека давало 60 б. на клиента — меньше минимального шага списания 50 б. | правило изменено на 10%, минимальный шаг согласован с демо-данными (`seed` увеличен до 12–20 покупок на клиента) |
| 2 | **Отмена операции уводила баланс в минус (−100)** | отменяемая проводка исключалась из суммы (`status='applied'`), а компенсирующая добавлялась — итог считался дважды | баланс считается по `status IN ('applied','reversed')`, добавлена ссылка `reverses_op_id` для аудита |
| 3 | `on_event("startup")` выдавал предупреждение об устаревшем API | FastAPI перешёл на lifespan | заменено на `@asynccontextmanager lifespan` |
| 4 | Дублирование списания при параллельной отправке | проверка ключа и вставка не были атомарны | `BEGIN IMMEDIATE` + `UNIQUE(idempotency_key)`, добавлен конкурентный тест |

Дефект №2 — самый показательный: он был найден автотестом, а не глазами, и именно
такого рода ошибки (двойной учёт при компенсации) в реальной системе приводят к
жалобам клиентов на «пропавшие» баллы.

## 5. Что проверено повторно после исправлений

- 14 автотестов, все проходят (`pytest -q` → 14 passed).
- Ручной прогон в браузере: начисление на кассе → баланс изменился и в приложении;
  списание в приложении → изменился на кассе; повторная отправка → `duplicate: true`,
  баланс изменился один раз; списание сверх баланса → отказ, баланс не тронут;
  отмена операции → баланс вернулся; несуществующая карта → понятное сообщение.
- Замеры: поиск клиента 0.9–1.1 мс (NFR-03 — ≤ 2000 мс), операция 8–26 мс
  (NFR-01 — ≤ 5000 мс).
